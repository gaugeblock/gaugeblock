# GB-347 — Remint legacy `GB-` keys in member stores

## Why this exists

Under the architect's model (`GB-346`, decided 2026-11-08):

- `GB-*` is the **harness**. Harness-level and multi-repository work only.
- Every repository mints under **its own** configured prefix: `BA BW CH CO DA JN MTR OF RB SH SP`.
- A ticket that proves to be single-repository work may be **reminted** into that repository.
- Harness work stays `GB-*` and is **linked** to the per-repository tickets carrying the work: `GB-NN -> SP-NN & OF-NN`.

The unified index enforces one key naming one ticket suite-wide, which is correct. It cannot open while six keys are owned twice, and **the collision count grows by roughly one per harness deferral** — the harness keeps minting numbers `storypole` already used. This ticket is the only open item whose defect count increments during normal work.

## What must be repaired, and what must not

Reminting a key without repairing what points at it leaves a live graph with edges to nothing.

**Repair (live pointers):**

1. `task_edges` rows whose `target_ticket_key` no longer exists.
2. `.storypole/plans/<KEY>.md` filenames, and the `TaskPlan` attachment that names them.
3. Ticket bodies that name other keys in prose — a reminted ticket quoting a dead key is a broken citation.
4. benchwork's DAG, which resolves keys to ids; a stale key shows as an edge to nothing.

**Never touch (history):**

5. `CHANGELOG.md` entries and commit messages. A remint changes what a ticket is called now, not what it was called when it shipped.

That boundary is the design: **history is immutable, live pointers are not.**

## Algorithm

1. **Map.** For each store, for each ticket whose key prefix is not the store's configured prefix, assign `<PREFIX>-<n>` continuing from the store's highest existing number of that prefix. Preserve `uuid`; that is the identity, and every reference by uuid still resolves. Write the mapping to a file and review it before anything moves.
2. **Dry run.** Report the mapping and the reference rewrite set. Change nothing.
3. **Rewrite.** Apply key changes and reference rewrites in one pass per store, so no intermediate state has a live pointer to a dead key.
4. **Verify.** Replay each store before and after; compare every reader-visible field except the key itself; refuse on any divergence. Then prove the graph: every edge target resolves, every plan file matches its ticket.
5. **Land.** Commit per repository, so a bisect can find the store that went wrong.

## Non-goals

- No renumbering to make keys contiguous. Gaps are harmless; churn is not.
- No touching the root store's `GB-*` keys. They are correct.
- No history rewriting of any kind.

## Risk

This mutates 195 tickets across eleven repositories. It is not a candidate for a hand-run script: it needs a verb (`storypole remint`) that can be tested, dry-run, and refused. The previous migration earned its safety from differential replay; this one earns it the same way.
