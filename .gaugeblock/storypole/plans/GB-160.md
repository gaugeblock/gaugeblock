# Task Plan: GB-160 — Suite Dependency and Feature Strategy Audit

> **Epic Key:** `GB-160` **Scope:** all eleven repositories + `miter` capability **Status:** Planned

---

## 1. Objective

Decide, from evidence, where a shared crate or a Cargo feature is warranted across the suite — and
where the honest answer is "leave it alone".

This exists because one extraction was right and three were guesses. `gaugeblock-contracts` was a
*layering* problem: six members carried copies of the same 42 wire types, ~890 lines came out, and the
repointing was mechanical. `miter-syntax`, `miter-inventory` and `gaugeblock-security` were proposed on
direct-dependency counts; `cargo tree` then showed every consumer already reaches `miter-engine`
transitively through `chalkline-core`, so repointing would have removed **zero crates**. A hunch about
weight is not a measurement.

---

## 2. The framing this audit applies

| Mechanism | Right when | Tonight's example |
|:--|:--|:--|
| **Crate extraction** | the *direction* of a dependency must change | `contracts` must sit beneath every member |
| **Cargo feature** | it is the same code in optional *weight* | `tokio` — you select the parts you need |
| **Do nothing** | one consumer, or the heavy dependency is genuinely needed | `chalkline`/`benchwork` need the inventory |

Most "split this out" instincts are the middle row wearing the top row's clothes.

---

## 3. Decision criteria (all three, or the answer is no)

1. **At least two consumers** use it — proved by `miter references`, not by intent or by a symbol's name.
2. **A measured reduction** in at least one consumer: fewer transitive crates *or* less clean build time.
3. **No dependency cycle**, and no heavy dependency pushed *down* onto every consumer.

Corollary: the audit is allowed to recommend deleting a crate, merging two, or adding nothing.

---

## 4. Evidence to collect

* `cargo tree -p <crate> -e normal` per consumer — total transitive size, and `-i <dep>` for the path.
* `cargo build -p <crate> --timings` on the heaviest consumers, before and after any change.
* `miter references/impact` for each candidate module — is it shared, or parochial?
* `miter clones` — duplication that would *justify* extraction.
* `miter skeleton` — the real size of an extracted API surface.
* `miter contracts` — schema drift after any move.

---

## 5. Phases

**P0 — Capability.** `miter` cannot currently answer the central question. `references` and `impact`
work per symbol; nothing aggregates *crate-to-crate* edges with symbol counts, and nothing understands
`#[cfg(feature = ...)]`. Add `miter deps`: per consumer crate, the provider crates it imports from and
how many distinct symbols, plus which items sit behind a feature gate. Without it this audit is
anecdote.

**P1 — Measure.** Run the evidence collection across all eleven repositories. No edits, no branches in
other repos.

**P2 — Report.** One section per repository: current dependency weight, candidates found, and a verdict
of *extract* / *feature* / *leave*, each with the numbers behind it. Publish as
`.gaugeblock/reports/dependency-strategy-audit.md` (or the repo's chosen doc path).

**P3 — Batch.** Group the surviving recommendations into one implementation epic, ordered so that each
step is independently gateable and bisectable.

---

## 6. Exit criteria

* Every repository has a written verdict, including the ones the audit clears.
* Every *extract* verdict cites a consumer count and a measured delta.
* `GB-157`, `GB-158`, `GB-159` are each explicitly closed, rescoped, or promoted with data.
* No production code changed during P0-P2 beyond the new `miter deps` capability.

---

## 7. Known constraints

* Local development resolves cross-repo crates through `.cargo/config.toml` `[patch.crates-io]`, so
  `cargo tree` reflects the working copies — good for honesty, but it means tree sizes are
  workspace-local and must be recorded as such.
* `chalkline-core` is the pivot: its use of `inspect_workspace` is why six repositories carry
  `miter-engine`'s 165-crate subtree. Any verdict that ignores that edge is wrong.
* No pushes, releases, publishes or version bumps are part of this epic.
